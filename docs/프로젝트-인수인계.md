# 노사교섭 레이더 프로젝트 인수인계

기준일: 2026-08-10  
대상: 한국 주요 제조기업의 **원청 법인 직접고용 노조** 임금·단체교섭 현황 대시보드

이 문서는 다음 담당자가 현재 구현 상태와 안전 경계를 빠르게 파악하고, 사실 데이터·수집기·데이터베이스를 안전하게 이어받을 수 있도록 작성했다. 환경 변수의 **이름만** 언급하며, 비밀값·접속 정보는 기록하지 않는다.

## 1. 현재 상태 요약

- 화면은 실제 법인명과 검증된 사실 데이터 스냅샷을 사용한다. 기준일은 `2026-08-10`이다.
- 런타임 화면의 데이터원은 현재 `data/historical-fact-seed.json`과 `data/current-2026-fact-seed.json`이다. 아직 Supabase에서 사실 데이터를 읽지 않는다.
- 2021–2025년 과거 데이터는 44건, 2026년 현재 데이터는 12건의 공개 가능 원청 직접고용 교섭 기록을 담는다.
- 원청·하청 범위 검토는 단계 분류보다 먼저 적용되는 필수 게이트다. 직접고용이 확인되지 않은 후보는 공개 단계·쟁점·노출도에 반영하지 않는다.
- 범위 판정은 2026-08-11에 개정했다. 배제는 어휘 신호로, 포함은 정식 교섭단위명(강한 근거)과 법인명 근처 노조·노사 표현(약한 근거) 두 등급으로 나눈다. 개정 전에는 정식명칭만 인정해 실제 원청 교섭 기사의 79%가 검토 대기로 빠졌다. 근거와 측정치는 [뉴스 데이터 파이프라인](./data-pipeline.md)에 있다.
- 일일 수집은 GitHub Actions `.github/workflows/daily-bargaining-update.yml`로 자동 실행된다. 수집 → 원문 URL 확인 → 사실 반영 → 회귀 검증 → 커밋 → 배포 순서로 동작한다. GitHub schedule 이벤트가 유실될 수 있으므로 KST 06:34·09:34·14:34 세 번 시도하고, 오늘 이미 성공했으면 첫 단계에서 건너뛴다. 별도 `수집 지연 감시` 워크플로가 멈춘 상태를 실패로 드러낸다. 자세한 근거는 [뉴스 데이터 파이프라인](./data-pipeline.md)에 있다.
- NAVER API HUB 자격증명 없이 Google News RSS를 주 수집원으로 쓴다. RSS 링크는 `scripts/resolve-google-news.mjs`가 발행사 원문 URL로 되돌린 뒤 도달 가능성과 제목 일치를 확인한다. 헤드리스 브라우저는 쓰지 않는다.
- 배포 단계는 Cloudflare Workers로 나가며 `CLOUDFLARE_API_TOKEN` 시크릿이 등록된 경우에만 동작한다. 없으면 경고만 남기고 저장소 데이터만 갱신된다.
- Supabase용 초기 마이그레이션과 Worker의 회사 추가 요청 API는 준비되어 있지만, 대상 Supabase 프로젝트 선정·마이그레이션 적용·사실 데이터 적재는 아직 완료되지 않았다.
- 서비스는 로그인 없이 공유 URL로 열람하게 설계되어 있다. 이는 **검색 비노출 정책**이지 URL 유출을 막는 인증 장치는 아니다.

## 2. 제품 범위와 핵심 원칙

### 공개 대상

대시보드의 관측 단위는 법인 브랜드가 아니라 다음 조합이다.

```text
법인 × 직접사용자 × 교섭연도 × 협약유형 × 교섭단위 × 적용 근로자 범위
```

공개 데이터에 포함하려면 아래 조건을 모두 충족해야 한다.

1. 선택한 회사 법인과 직접사용자 법인이 일치한다.
2. 노조의 적용 근로자가 해당 법인의 직접고용 근로자다.
3. `scopeClassification = PRIMARY_DIRECT_UNION`이다.
4. `coveredWorkerRelation = DIRECT`이고 `includeInPrimaryDashboard = true`다.
5. 공개 전 사람 또는 규칙 기반 검증을 통과한 사실이다.

하청·사내협력사·용역·파견 노조가 원청을 상대로 교섭을 요구하는 사례는 중요하더라도 이 제품의 공개 범위가 아니다. 해당 후보는 감사·검토 대상으로만 보관한다. 원청 상대 교섭 요구, 원청 이름, 본사 앞 집회라는 표현만으로 직접고용을 추정하면 안 된다.

### 단계와 병렬 상태

주 단계는 완료율이 아닌 현재 교섭 좌표다. `U`, `S0`–`S8`을 사용하며, 조정·쟁의·대표성·잠정합의·인준·서명·이행 상태는 별도로 보존한다.

- `S5` 잠정합의는 최종 체결이 아니다.
- `S6` 조합원 찬반투표·인준은 조인·서명이 확인되기 전 단계다.
- `S7`은 서명·조인·발효가 확인된 경우에만 사용한다.
- 파업 투표 또는 실제 파업 보도만으로 교섭 결렬·조정 단계인 `S4`를 자동으로 만들지 않는다.
- 새 기사가 없다고 이전 상태를 미착수로 되돌리지 않는다.

상세 기준은 [교섭 프레임워크](./negotiation-framework.md), 수집기 규칙은 [뉴스 데이터 파이프라인](./data-pipeline.md)을 우선 참고한다.

선정 기준은 규모·산업 파급력 30%, 대표성 데이터 준비도 20%, 최근 24개월 직접고용 교섭 노출도 25%, 직접고용 교섭구조 복잡성 25%다. 기사 수만으로 노출도를 세지 않으며, 하청·간접고용·범위 미확인 사례는 제외한다. 세부 기준과 T1/T2/T3 관찰군은 `data/company-universe.json`에 있다.

### 2021–2025년 과거 데이터

- 범위: 12개 법인 × 5개 연도 = 60개 법인·연도 슬롯
- 공개 가능 사실 레코드: 44건
- 검토한 원천 레코드: 52건
- 근거 또는 범위 미확인으로 보류된 연도 슬롯: 16개
- 하청·혼합 등 격리 후보: 6건
- 공개 시드에는 `PRIMARY_DIRECT_UNION`이고 `includeInPrimaryDashboard = true`인 레코드만 들어간다.

과거 시드는 한 법인·연도마다 하나의 대표 교섭 기록만 담을 수 있다. 데이터가 없는 연도는 교섭 미착수나 타결이 아니라 **원청 직접고용 범위와 교섭 사실을 함께 확인하지 못한 상태**다. UI는 그 경우 `U`로 표시한다.

`bargainingYear`와 `eventDate`는 다르다. 예를 들어 특정 연도의 협약이 이듬해 보도·서명되거나 과거 사실이 뒤늦게 확인될 수 있으므로, 연도 필터의 교섭연도와 기록 일자를 혼동하지 않는다.

## 5. 원청·하청 범위 검토 Skill과 서브에이전트

개인 Skill 경로는 다음과 같다.

```text
/Users/frypaneggnaver.com/.codex/skills/primary-union-scope-review/
```

현재 규칙 버전은 `1.1.0`이다. 수집기 설정의 `scopeReviewAgent`도 같은 버전을 사용하며, 반드시 `before_stage_classification` 순서로 실행한다.

### 분류값과 처리

| 분류 | 공개 처리 |
| --- | --- |
| `PRIMARY_DIRECT_UNION` | 직접사용자와 적용 근로자 범위가 모두 확인된 경우에만 후속 단계·쟁점·대표성 처리 |
| `SUBCONTRACTOR_UNION_EXCLUDED` | 하청·사내협력사·용역·파견 등. 비공개 감사 대상으로 격리 |
| `AFFILIATE_UNION_EXCLUDED` | 별도 계열사 또는 별도 법인 노조. 비공개 감사 대상으로 격리 |
| `MIXED_NEEDS_SPLIT` | 원청·간접고용 사실이 섞여 자동 분리 불가. 사람 검토 대기 |
| `UNKNOWN_REVIEW` | 직접고용 근거가 없거나 충돌. 사람 검토 대기 |

### 과거 법인명 주의

- 한화오션 주식회사: 대우조선해양 주식회사 시절의 교섭 기록은 상호 변경 근거와 별도로 직접고용·교섭 근거를 보존한다.
- 두산에너빌리티 주식회사: 두산중공업 주식회사 시절의 교섭 기록도 같은 원칙을 적용한다.
- HD현대중공업 주식회사: 현대중공업·그룹·계열사·사내하청 조직을 회사명만으로 합치지 않는다.

상호 변경은 법인 연속성 보조 근거일 뿐 직접고용 범위를 증명하지 않는다. 과거 기사에 법인·노조·직접고용 적용범위가 함께 확인되지 않으면 `UNKNOWN_REVIEW`으로 남긴다.

### Skill 갱신 원칙

법률·시행령·행정지침 또는 지배적 판례가 바뀌면 Skill의 `references/legal-update-protocol.md`를 먼저 따른다.

1. 근거 URL, 시행일, 영향 규칙을 소비 프로젝트의 법률 근거 장부에 기록한다.
2. 변경이 감사 문구·증거 요건·제품 범위 중 무엇에 영향을 주는지 판단한다.
3. 제품 소유자가 범위 변경을 명시 승인하지 않는 한 직접고용 공개 게이트를 완화하지 않는다.
4. 규칙 버전, 판단 신호, 회귀 사례, 출력 레코드의 `rule_version`을 함께 갱신한다.
5. 직접고용·하청·파견·계열사·혼합·과거 법인명 회귀 사례를 다시 실행한다.

이 Skill은 법정 사용자성에 대한 일반적 법률 결론을 내리는 도구가 아니다. 오직 이 대시보드에 원청 직접고용 노조 사례만 넣기 위한 보수적 필터다.

## 6. 일일 뉴스 수집과 사실 반영

### 수집기 구성

- 실행 파일: `scripts/collect-news.mjs`
- 설정: `data/source-config.json`
- 주 수집원: NAVER API HUB 뉴스 검색(날짜순)
- 보조·대체 후보 탐색: Google News RSS
- 기사 본문·검색 API 설명문은 저장하지 않는다. 제목·매체·발행일·원문 URL과 프로젝트가 계산한 분류만 저장한다.
- 기본 출력: `public/data/news-candidates.json`

권장 주기는 모든 법인에 대해 한국 표준시 매일 06:30, 법인별 1회다. 같은 KST 날짜에 완료한 배치는 중복 실행을 막고, 장애 복구·규칙 검증 때만 `--force`를 사용한다. 모든 수집 쿼리가 실패하면 기존 결과를 보존하도록 설계되어 있다.

### 반영 순서

1. 법인별 검색어로 뉴스 후보를 수집한다.
2. 대상 연도·URL·노사관계 신호를 확인하고 URL·제목으로 중복을 제거한다.
3. **원청 직접고용 범위 검토 Skill을 먼저 실행**한다.
4. `PRIMARY_DIRECT_UNION`인 후보만 회사·교섭단위·주 단계·병렬 상태·쟁점을 분류한다.
5. `eligibleForStatusAggregation = true`이고 원문·출처가 확인된 후보만 상태 집계 후보가 된다.
6. RSS 단독 후보나 원문 URL이 없는 후보는 `requiresSourceVerification = true`로 남겨 사람 확인 전 공개 상태를 바꾸지 않는다.

수집기 출력은 `scripts/apply-daily-update.mjs`를 통해 `current-2026-fact-seed.json`을 자동 갱신한다. 반영 대상은 원청 노조 범위 검토와 원문 URL 확인을 모두 통과한 후보이며, 갱신 범위는 단계·발생일·제목·원문 URL·매체·신뢰도·교섭 경과로 제한한다. 노조명, 직접고용 범위 근거, 범위 증빙 URL, 법인명은 기사 제목으로 추정할 수 없으므로 기존 값을 유지한다.

과거 시드(`historical-fact-seed.json`)는 자동 갱신하지 않는다. 추적 목록에 없는 법인도 자동으로 추가하지 않는다.

자동 반영 기록은 `factualStatus = "AUTO_COLLECTED_TITLE_BASIS"`로 표시되어 사람이 검증한 `VERIFIED_SOURCE`와 구분된다. 사람이 검증한 `S7`·`S8` 체결 기록은 같은 등급 근거 없이 하위 단계로 되돌아가지 않는다. 실행 이력은 `data/daily-update-audit.json`에 남는다.

### 실행과 점검

```bash
npm install
npm run dev
npm run lint
npm test

# 수집기 문법·설정 확인
node --check scripts/collect-news.mjs

# 파일을 쓰지 않는 후보 수집 진단
node scripts/collect-news.mjs --dry-run --source google --max-per-query 3

# 과거·현재 사실 시드 재생성
node scripts/build-historical-seed.mjs
node scripts/build-current-2026-seed.mjs
```

뉴스 수집을 주 수집원으로 실행하려면 서버 런타임에 NAVER API HUB 자격증명이 필요하다. 자격증명 이름과 실행 옵션은 [뉴스 데이터 파이프라인](./data-pipeline.md)에만 참고하고, 값을 문서·소스·클라이언트에 기록하지 않는다.

`npm test`는 빌드와 렌더링 검증을 포함한다. 특히 검색 비노출 헤더와 메타태그, 12개 법인·2026년 시드, 원청 직접고용 검증 필드, Supabase 미설정 시 회사 추가 API의 `503` 응답, 하청 기사 격리 회귀 사례를 검사한다.

## 7. Supabase: 설계 완료, 실제 연결·적재 미완료

현재 Supabase는 다음 상태다.

- 초기 스키마 파일: `supabase/migrations/20260810_initial_bargaining_dashboard.sql`
- 운영 절차: `docs/supabase-setup.md`
- **미완료**: 대상 Supabase 프로젝트 확정, 마이그레이션 적용, 초기 데이터 적재, RLS 실환경 검증, 대시보드 읽기 전환, 일일 적재 자동화
- 현재 화면은 Supabase가 아니라 정적 JSON을 import한다.
- Worker의 Supabase 호출은 회사 추가 요청을 `company_add_requests`에 적재하려는 경로뿐이다. 일반 사실 데이터 조회·적재 API는 아직 구현되어 있지 않다.

### 설계된 테이블

`tracked_companies`, `union_profiles`, `union_governance_events`, `bargaining_cases`, `bargaining_case_unions`, `bargaining_events`, `bargaining_issues`, `bargaining_terms`, `sources`, `source_annotations`, `scope_review_audits`, `company_add_requests`를 설계했다.

모든 `public` 테이블은 RLS를 켜고, 익명 역할에는 검증·공개된 직접고용 사실의 읽기만 허용하도록 마이그레이션에 정의되어 있다. `scope_review_audits`와 `company_add_requests`에는 공개 읽기 정책을 만들지 않는다.

### Supabase 적용 전 필수 순서

1. 제품 소유자가 대상 Supabase 프로젝트를 명시적으로 확정한다.
2. 서버 전용 환경 변수만 배포 런타임에 설정한다. 필요한 변수 이름은 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `DASHBOARD_ADMIN_CODE`이며, `SUPABASE_PROJECT_REF`는 선택 사항이다.
3. 초기 마이그레이션을 한 번 적용한다. 다른 서비스 데이터베이스에 임의 적용하면 안 된다.
4. 공개 스키마·RLS·권한·인덱스에 대한 보안 권고 도구를 실행한다.
5. 원문 URL·직접고용 범위·검증 상태가 완결된 12개사 사실 데이터만 적재한다.
6. 익명 역할로 공개 행만 조회되는지, 하청·혼합 감사 기록과 회사 추가 요청이 전혀 보이지 않는지 검증한다.
7. Worker API가 `PENDING` 요청만 생성하고, 비밀값·관리 코드가 응답·로그에 남지 않는지 검증한다.

`SUPABASE_SERVICE_ROLE_KEY`와 관리 코드는 브라우저, `NEXT_PUBLIC_` 변수, 정적 파일, 로그에 절대 넣으면 안 된다. 서비스 역할 키는 RLS를 우회하므로 Worker/서버에서만 사용한다.

## 8. 추적 기업 추가 기능

화면의 “추적 기업 추가” 모달은 법인 실명, 산업, 참고 URL, 추가 사유, 운영 관리 코드를 받아 `POST /api/company-requests`로 보낸다.

Worker는 다음을 수행한다.

1. 요청 방식과 입력 길이·URL 형식을 확인한다.
2. 헤더의 관리 코드를 서버의 `DASHBOARD_ADMIN_CODE`와 상수 시간 비교한다.
3. Supabase 서버 역할 키로 `company_add_requests`에 `PENDING` 행만 만든다.
4. 코드 원문은 데이터베이스에 저장하지 않는다.

현재 Supabase 환경 변수가 없으므로 이 API는 의도적으로 `503`을 반환한다. 즉, UI는 배포되어도 공개 사용자가 임의로 기업을 추가하는 상태가 아니다.

추가 요청을 실제 공개 법인으로 전환하려면 사람이 법인 실명·법인 ID·직접고용 노조·원문 근거·초기 교섭 기록을 검토하고, `tracked_companies`와 관련 데이터에 별도로 등록해야 한다. `PENDING` 요청을 자동 공개하면 안 된다.

`docs/supabase-setup.md`에는 엔드포인트의 속도 제한을 둘 것을 명시한다. 현재 `worker/index.ts`에는 속도 제한 구현이 없으므로, Supabase 연결 전 또는 동시에 IP·코드 단위 속도 제한과 감사 로그 최소화 정책을 구현해야 한다.

## 9. 배포, 공유 접근, 검색 비노출

### 배포 구조

- 빌드·개발 런타임: Vinext/Vite + Cloudflare Worker
- 운영 배포 대상: Cloudflare Workers. 워커 이름은 `er-radar`이고 계정 workers.dev 서브도메인도 `er-radar`다.
- 수동 배포: 저장소 루트에서 `npx wrangler deploy`. `.wrangler/deploy/config.json`이 빌드 산출물의 `dist/server/wrangler.json`을 가리키므로 별도 설정 인자는 필요 없다.
- 자동 배포: 일일 워크플로의 배포 단계가 `CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID` 시크릿으로 같은 명령을 실행한다.
- 워커 설정은 `vite.config.ts`의 `localBindingConfig`가 원본이다. `assets.binding`을 선언하지 않으면 배포본에서 `env.ASSETS`가 `undefined`가 되어 정적 자산이 서빙되지 않는다. `preview_urls`는 꺼 두어 공개 주소를 workers.dev 한 곳으로 묶는다.
- `.openai/hosting.json`은 D1·R2 바인딩 여부만 알려주는 입력으로 남아 있고 둘 다 사용하지 않는다. 과거 배포 경로였던 `sites` 원격은 자격증명이 없어 사용하지 않는다.
- 배포 URL은 소스에 고정하지 않는다. 인수인계 시 운영자에게 현재 배포 주소와 배포 권한을 별도로 확인한다.

### 로그인 없는 공유와 비색인

현재 페이지는 로그인 요구 경로를 호출하지 않는다. `app/chatgpt-auth.ts`에는 ChatGPT 인증 보조 함수가 남아 있으나, 현재 대시보드 페이지에서 이를 import하거나 사용하지 않는다. 로그인 흐름을 다시 연결하지 않도록 주의한다.

검색 비노출 조치는 다음과 같다.

- Worker가 모든 응답에 `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet, noimageindex`를 붙인다.
- `app/layout.tsx`가 동등한 로봇 메타태그와 `nocache`를 설정한다.
- `public/robots.txt`가 모든 경로를 차단한다.
- Open Graph와 X 카드 메타데이터를 설정하지 않는다.

이 조치는 검색엔진·미리보기 수집기의 노출을 줄일 뿐이다. URL을 아는 사용자의 접근을 막지 않으며, 공유 URL은 외부 공개 게시물·검색 가능한 문서에 넣지 않아야 한다. URL 유출 자체를 차단해야 한다면 비밀번호·인증·접근제어 계층을 별도 도입해야 한다.

배포 후에는 익명 브라우저에서 로그인 리디렉션 없이 `200`을 받는지, 응답 헤더와 HTML 메타태그가 모두 비색인 상태인지 확인한다. 이미 색인이 발생했다면 검색엔진별 삭제 도구를 별도로 사용한다.

## 10. 후속 작업 우선순위

1. **Supabase 실제 개통**: 대상 프로젝트를 확정하고 초기 마이그레이션·RLS·익명 읽기 제한을 적용·검증한다.
2. **정적 시드에서 DB 읽기로 전환**: 12개사·2021–2026 검증 사실을 적재하고, UI가 공개·검증된 DB 행만 읽도록 구현한다. 정적 시드와 DB의 중복·정정 이력을 결정한다.
3. **배포 자동화 점검 유지**: Cloudflare 자동 배포는 2026-08-10에 연결했다. 남은 일은 감시다. 토큰에 만료(TTL)를 걸어 두었다면 만료일 이후 배포 단계가 조용히 실패하므로, 사실이 바뀐 날의 워크플로 실행 결과와 실제 공개 URL의 갱신 여부를 함께 확인한다.
4. **원청·하청 회귀 검증 유지**: 매 수집·법률 변경·상호 변경·새 법인 추가 시 Skill의 회귀 사례를 실행하고 규칙 버전을 기록한다.
5. **회사 추가 운영 보강**: 속도 제한, 운영자 검토 화면, `PENDING → APPROVED/REJECTED` 처리, 법인·직접고용 근거 검증 절차를 구현한다.
6. **사실 데이터 보강**: 2021–2025년 16개 미확인 법인·연도 슬롯을 우선 조사하되, 근거가 부족하면 `U`를 유지한다. 조합원 수·과반 교섭창구·노조 선거·쟁점·최종안 변경도 근거 URL과 기준일이 있을 때만 추가한다.
7. **운영 보안 확인**: Workers 비밀값 노출, RLS 우회 경로, 공개 API 권한, 헤더·robots 적용, URL 유출 대응을 배포 때마다 점검한다.

## 11. 변경 시 지켜야 할 주의사항

- 사실 데이터는 기사 제목이나 회사명만으로 추정하지 않는다. 원문 URL, 교섭 확인일, 직접고용 범위 근거, 출처 등급을 함께 보존한다.
- 기사 본문·장문 인용문을 복제·저장하지 않는다.
- `S6`을 `S7`로 올리려면 조합원 가결이 아니라 서명·조인·발효 근거가 필요하다.
- 과반 노조 `O/X`는 전체 직원 대비 가입률이나 대표교섭노조 여부가 아니다. 참여 노조 범위, 분자·분모, 기준일, 근거 URL이 모두 있을 때만 표시한다.
- 하청·간접고용 사례는 원청 대상 교섭이라도 공개 대시보드에 섞지 않는다. 감사 보관과 공개 상태 갱신을 분리한다.
- 법률 변화가 있어도 제품 소유자의 명시 승인 없이 직접고용 공개 범위를 넓히지 않는다.
- 데이터 정정은 기존 행을 조용히 덮어쓰기보다 원문 URL·검증 시각·정정 주석을 남겨 추적 가능하게 한다.
- `.env`, 배포 환경 변수, 서비스 역할 키, 관리 코드, 외부 API 키를 문서·소스·테스트·로그에 넣지 않는다.
